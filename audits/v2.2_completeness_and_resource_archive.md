# v2.2 优化记录：全库完整性门禁与正文资源归档

执行日期：2026-08-20

## 一、为什么需要新增这一层

原始数据库已经保存全部详情 HTML 和常规附件，但原下载器仅识别 PDF、Word、Excel、压缩包等扩展名，没有系统归档正文区域中的图片，也没有跟随旧版 JavaScript 正文跳转。对于图片表格、扫描件和历史结算参数页面，这会造成“HTML文件存在，但离线无法完整还原正文”的隐性缺口。

回补程序处理1,584个唯一资源URL，成功1,545个；成功文件对应1,518个唯一内容哈希，说明存在少量跨URL重复内容，已自动去重。

正文依赖资源的可归档覆盖率为：

`(1657 + 1 + 3) / 1697 = 97.88%`

剩余36个引用均有明确状态，而不是未发现的静默缺口。

- notice_id；
- 资源URL与类型；

- SHA-256；

## 五、统一完整性门禁

新增快速与全哈希两种模式。门禁同时检查：

1. 官方API目录与原始数据库URL集合是否一致；
2. 公告和附件数据库状态；
3. 本地路径、文件大小及可选SHA-256；
4. 原始库和标签库SQLite完整性；
5. 原始库与标签库公告数是否一致；
6. notice_id、source_url和event_id重复；
7. 空正文、正文资源覆盖和人工确认事件状态。

## 六、尚未消除但已量化的缺口

1. 3个常规附件源端失效。
2. 34个正文资源源端不可取。
3. 2个正文图片引用是发布者本机路径，无法从互联网解析。
4. 47条正文仍为空，其中包含待OCR图片、旧DOC和失效历史跳转。
5. 参数事件仍未完成人工验证。

这些项目均以warning进入门禁报告；目录不一致、文件缺失、哈希错误、数据库损坏或原始库与标签库数量不一致会直接触发FAIL并阻止发布。

## 七、论文意义

优化前只能证明“详情页HTML与常规附件基本齐全”；优化后可以进一步证明：

- 全部公告详情页均参与资源依赖审计；
- 正文图片和旧版正文跳转被独立识别；
- 可取得资源按哈希归档和去重；
- 不可取得资源具有明确、可复查的失败证据；
- 8,355个原始公告及常规附件通过全量哈希验证。
